# 個人首頁開發計畫

以 SDD 1.0.0 與深海青綠設計規範為開發基準。本機產生器與更新設定已實作；各階段的實際完成與阻擋狀態見 [實作狀態](IMPLEMENTATION-STATUS.md)。各階段依序進行，不需要為已確認的情境與工作流重新提問。

## 1 開發順序

| 階段 | 工作與產出 | 完成條件 |
| --- | --- | --- |
| D1 資料與環境 | 確認 Node LTS、Git 狀態與目標同名 repo；唯讀核對候選專案；試查 API 權限與欄位；建立設定契約 | 記錄 API 能力、所需 token、版本及 2 至 3 個作品草稿；若缺 token，fixture 開發照常進行 |
| D2 靜態首頁 | 建立 README 模板、Hero、tokens 讀取、原生作品與介紹 | 本機可產生有正確圖片路徑的 README；無假數字、無空連結 |
| D3 資料與統計 | GitHub client、分頁、白名單快照、metrics、runtime validation | 資料與邊界測試通過，取得失敗不改正式產出 |
| D4 SVG 與替代內容 | 活動、Streak、Languages、Monthly、Calendar 元件；details 資料表 | 所有圖與文字源自相同快照；320 px 可讀，大小符合規範 |
| D5 更新工作 | check 與 update workflows、憑證分離、並行控制、無差異跳過、推送衝突處理 | PR 無寫權限；手動更新成功；模擬失敗保留上一版本 |
| D6 平台驗收 | GitHub 真實 README 預覽、明暗模式、手機寬度、連結與快取檢查 | ACCEPTANCE 的必要項目全部有結果；遠端部署與權限實測完成 |

可獨立進行的是內容草稿與 fixture 元件；實際 API、遠端推送與 GitHub 渲染驗證依賴可用帳號與儲存庫。這些依賴只阻擋對應階段，不需提前阻擋所有開發。

## 2 起始工作清單

- [ ] 讀取工作區與上層適用的 AGENTS 指示，沿用已確認的 Web 開發與不使用工作流。
- [ ] 先看 `git status` 與 remote；不存在 repo 時再依需要初始化，不 reset 既有資料。
- [ ] 驗證同名遠端是否存在，存在時取得原內容並比較，避免用本地文件覆蓋原首頁。
- [ ] 將目前規格入口保存為 `docs/PROJECT-GUIDE.md`，再建立正式首頁模板。
- [ ] 固定 Node 與 API 版本，建立鎖檔、`.gitignore` 與指令契約。
- [ ] 先做 D1 的最小 API 試查，將不支援欄位或權限差異反映到 SDD。
- [ ] 建立合成 fixtures，標記只供測試，禁止其進入正式更新路徑。
- [ ] 開始 D2，不先安裝完整網站框架或常駐資料庫。

## 3 版本規劃

第一版完成 SDD 的全部必要元件與驗收，不把連續貢獻或資料正確性留到後續補救。後續可選功能為全生涯統計、可切換卡片主題、作品截圖及更細部的自動選文；都需另定統計成本、更新規則或內容來源。

## 4 發布與回復

發布候選必須包含真實快照、生成檔 diff、GitHub 實際渲染結果及驗收紀錄。正式變更前確認遠端目標為本人同名儲存庫，保留既有首頁可回復的 commit。將設定／模板與生成檔分開維護，發布生成檔用單一 commit。

完成後以 profile URL 檢查圖片和連結，不以 Git push 成功代替驗收。若資料或圖片錯誤，停用有問題的更新工作、revert 生成 commit，再修正與重跑；不要清空 README。

## 5 開發紀錄格式

每階段紀錄實際變更、執行指令、檢查結果及尚未驗證的外部條件。`npm test` 通過不代表 Github 渲染已通過；API 試查成功不代表排程已啟用。依事實更新完成狀態。
